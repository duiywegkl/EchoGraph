# 需求：图谱跟随聊天时间线

状态：需求已全部确认，进入调查阶段
最后更新：2026-11-13

## 1. 背景

在 SillyTavern（以下简称“酒馆”）里，用户可以对任意回复反复重新生成（swipe）并来回切换，也可以编辑消息、删除消息、回退到第 N 轮，还可以从某条消息创建分支或检查点。

现在的滑动窗口、处理延迟和冲突解决，都是为了绕开这个问题：延迟处理，只收录“已经稳定”的轮次。这个办法很粗糙，图谱经常和屏幕上的聊天对不上。

本需求的目标是让图谱始终和**当前显示的那条聊天时间线**完全一致。

## 2. 范围与原则

| 编号 | 需求 |
|---|---|
| R1 | 每个聊天单独一张图。同一个角色的不同聊天，图谱互不影响。 |
| R2 | 图谱和当前显示的时间线保持一致：重新生成、切换 swipe、编辑、删除、隐藏、回退之后，图谱都要跟着变。 |
| R3 | 支持酒馆的分支和检查点。分出来的聊天，从分叉点那一刻的图谱开始继续往下走。 |
| R4 | 只通过插件和酒馆交互，桌面程序不直接连接酒馆。官方扩展接口不够用的时候，允许插件里写侵入式的 JS，但要说明它有多脆弱。 |
| R15 | 本地模式是正式功能，同样支持分支和重新生成。两种模式共用同一套核心逻辑（时间线 + 图谱版本），酒馆插件和本地界面只是两个不同的入口。 |

## 3. 基础图与开局

| 编号 | 需求 |
|---|---|
| R10 | 每个角色存一份**基础图**，只包含角色卡描述和世界书的内容。新聊天从基础图复制一份起步，不重复调用 LLM。 |
| R8a | 基础图是否需要重建，由角色卡和世界书内容的 hash 判断。hash 变了就重建基础图；已有的聊天保持不动，只有之后新开的聊天使用新的基础图。 |
| R11 | **开局**就是聊天的第 0 条消息，按第 0 轮处理。一张卡的多个开局（`first_mes` 和 `alternate_greetings`）在酒馆里显示为第 0 条消息的不同 swipe，所以切换开局和切换 swipe 走同一套逻辑。“重来”就是新开一个聊天，旧聊天连同它的图谱一起保存。 |
| R16 | 本地模式：一进来就有一个默认对话（0 号对话），已经放好了图谱和开局。之后“新建对话”得到的是完全空白的对话：没有开局，也没有图谱。 |
| R17 | 现有的按角色共用的旧图（`data/tavern_characters/*/sessions/current`）直接丢弃，不做迁移。 |
| R5 | 导入或复制的聊天：如果能确认它来自哪个聊天，就继承那个聊天的图谱；确认不了，就根据聊天记录重新生成。 |

### 3.1 调查后补充的决定

| 编号 | 需求 |
|---|---|
| R18 | 基础图只收录角色卡里跟剧情有关的字段：`name`、`description`、`personality`、`scenario`、`mes_example`。不收录 `creator_notes`、`system_prompt`、`post_history_instructions`。开局（`first_mes`、`alternate_greetings`）也不收录，它属于第 0 轮。 |
| R19 | 世界书分三类处理：<br>- 角色主绑定、附加绑定和卡内嵌的世界书，进**基础图**，参与 hash 计算。<br>- 聊天绑定的世界书，进**这个聊天自己的图**。<br>- 全局世界书和 Persona 世界书默认**不收录**，作为配置项，默认关闭。<br>插件按来源用 `loadWorldInfo(name)` 一本一本地读。 |
| R20 | `/sys` 旁白消息（`extra.type='narrator'`）算剧情，收录进图谱。 |
| R21 | 以下消息不进图谱：<br>- 系统通知、`/comment` 注释、工具调用消息，按类型排除。<br>- 用户或角色发的普通消息，如果 `is_system===true`，视为被隐藏，也排除。<br>以后插件每次发现消息被隐藏，都写一个自己的持久标记。 |
| R22 | 本地模式：第一次启动时自动创建示例对话，界面上显示为 0 号，内部仍然用 UUID。之后“新建对话”得到的一律是完全空白的对话，不再弹框询问。 |
| R23 | 两个节点之间允许有多条关系（多重边），每条边有自己的稳定 ID。 |
| R24 | 手动编辑的图谱放在单独一层，和时间线无关，一直保留。<br>- 实际显示和使用的图谱 = 时间线当前的图谱 + 按顺序叠加的手动编辑。<br>- 某条手动编辑引用的节点或边在当前时间线里已经不存在时，跳过这条编辑，并在界面上提示被跳过了几条。<br>- 分支或派生出来的聊天，复制一份父聊天的手动编辑层。 |
| R26 | 群聊（低优先级，用户几乎不用）：基础图由所有成员的角色卡和各自绑定的世界书合并而成，归属为该群；任何成员的卡变了都会重建基础图，已有群聊保持不动。 |
| R25 | 手动编辑支持 Ctrl+Z（撤销）和 Ctrl+Y（重做），图谱页上也有对应的按钮。<br>- 撤销和重做的历史保存在磁盘上，重启程序后仍然可以继续撤销。<br>- 撤销之后又做了新的编辑，被撤销的那部分就不能再重做了，和常见的编辑器一样。<br>- 只针对手动编辑；LLM 生成的部分跟着时间线走。 |

## 4. 时间线事件与图谱的变化

| 事件 | 对图谱的影响 |
|---|---|
| 新的一轮回复 | 调用 LLM 提取，结果作为这一轮的增量保存。 |
| 重新生成（新的 swipe）| 每次都调用 LLM。每个 swipe 的结果单独保存（R13）。 |
| 切换到一个已经生成过的 swipe | 直接使用保存好的结果，不再调用 LLM。 |
| 删除或回退到第 N 轮 | 图谱恢复到第 N 轮的状态。 |
| 编辑第 N 轮 | 回到第 N 轮之前的状态，从第 N 轮到最新一轮重新生成（见第 5 节）。第 N 轮之后、那些没被选中的 swipe 的结果作废。 |
| 隐藏或取消隐藏第 N 轮（R12）| 被隐藏的消息不进图谱。隐藏或取消隐藏中间的某条消息，按“编辑第 N 轮”处理。 |
| 分支或检查点 | 新聊天继承父聊天在分叉点的图谱。 |

非当前 swipe 的内容不进图谱，只有当前显示的那个 swipe 算数。

## 5. 编辑后重新生成（R14）

### 5.1 两种方式（配置项）

- **配置项**：“编辑后逐轮重新生成”，**默认不勾选**。
  - **不勾选**：把第 N 轮到最新一轮一次性发给 LLM。LLM 返回一整块结果，每个实体和关系都要标上来自第几轮（`turn` 字段），系统再按轮次拆成每一轮的增量。
  - **勾选**：一轮一轮依次处理。更准确，但调用次数更多。

### 5.2 输出校验

- LLM 返回的 JSON 只要不符合格式，就算失败。比如：解析出错、字段类型不对（字符串变成数字，或者反过来）、缺少 `turn`、`turn` 不在这次发送的轮次范围内。
- 失败了就把错误打回给 LLM 修正，最多重试 3 次。这复用现在的修复流程：先在本地尝试修复，再让 AI 修复，最多 3 轮。
- 3 次都失败了就报错。失败之后怎么恢复，见第 5.4 节。

### 5.3 分段与 token 估算

- **估算规则**（不用 tokenizer，直接数字数）：
  - 汉字：每个算 2 个 token。
  - 英文单词：每个算 2 个 token。
  - 标点、空格、数字：每个算 1 个 token。
- **能拿到模型上下文大小时**：发送的内容（包括提示词和当前图谱）最多占上下文的一半，另一半留给输出。估算超了就分段发送。
- **拿不到上下文大小时**：整段发送。
- **出错就对半拆**：不管报的是什么错，只要请求出错，就把这次的内容拆成 2 份重试；还出错就拆成 4 份，再出错拆成 8 份。下一次要拆成 16 份，超过了 10 份的上限，就停下来报错。所以算上第一次整段发送，一共最多试 4 次。估算后已经分好段的请求，出错时也按同样的规则继续拆。
- 拆分的最小单位是一整轮，不会把一轮消息从中间切开。某一轮单独发送仍然出错，就停下来报错。
- 初始化和重新生成都不限制最大输出（R9）。

### 5.4 失败后的恢复

- 重新生成在一份临时副本上进行，全部成功后才替换当前图谱。中途失败的话，当前图谱保持编辑前的样子，不会只更新一半。
- 已经成功的分段保存下来，重试时从失败的那一段接着做。
- 界面（插件和本地界面）上标出“图谱与聊天不一致”，并提供“重试”按钮。

## 9. 调查

### 9.1 第一轮（已完成，读源码）

结论摘要：

- **聊天 ID**：酒馆没有稳定的聊天 ID。文件名在重命名时会变，只能由插件往 `chat_metadata` 里写入自己的 UUID。这个 UUID 会随 `.jsonl` 文件一起保存。
- **消息 ID**：酒馆没有稳定的消息 ID，用的是数组下标，中间删除或插入一条，后面的下标就全变了。插件要给每个 swipe 都写一个 UUID，写在 `swipe_info[].extra` 里。原因是切换 swipe 时，酒馆会把 `extra` 换掉。
- **事件不完整**：
  - 分支、检查点、隐藏消息都没有对应的事件。
  - `MESSAGE_DELETED` 只传删除后的聊天长度，不说删的是哪一条。
  - 所以每次收到事件，插件都要拿完整的 `context.chat` 重新核对一遍，正确性靠核对来保证。
- **分支和检查点**：会生成一个新的聊天文件，`main_chat` 字段里只记了父聊天的文件名。分叉点要靠比对父子两个聊天的消息 UUID 来推断。要在检查点创建的那一刻就准确记录，只能用侵入式拦截，风险高。
- **导入和复制消息**：都会把我们写入的 UUID 原样复制过去，所以核对时要检查 UUID 是否重复，重复的重新分配。
- **读取其他聊天**：可以调用 `/api/chats/get` 读取，但这是内部接口，不在官方扩展 API 里，兼容性有一定风险。
- **升级到 1.19.0**：插件没有被破坏。但删除一条回复时，可能会连带删掉它前面的工具调用消息。

   - hash 具体对哪些内容计算。
3. **R12 隐藏消息**：区分“用户隐藏的消息”和本来就是系统消息的那些（比如旁白 `/sys` 和各种提示消息），两者都是 `is_system=true`。
4. **5.3 节的上下文大小**：现有的 `model_catalog` 能拿到哪些模型的上下文大小；拿不到的情况有哪些。
5. **第 6 节本地模式**：

7. **实测**（报告里的第 1 阶段）：在真实运行的酒馆里，用一个临时测试聊天把下面这些操作逐个做一遍：swipe、删除、编辑、隐藏、分支、检查点、重命名、导入。记录每一步的事件顺序，确认写进 `swipe_info[].extra` 的 UUID 能保留下来。

### 9.2.1 实测结果（2026-11-13，酒馆 1.19.0，临时角色“EG测试”）

| 操作 | 触发的事件 | 结果 |
|---|---|---|
| 新建聊天（卡上有 3 个开局） | `CHAT_CHANGED`、`CHAT_CREATED`、`MESSAGE_RECEIVED(0,'first_message')` | 3 个开局就是第 0 条消息的 3 个 swipe。**R11 成立。** |
| 切换开局 | `MESSAGE_SWIPED(0)` | 和普通 swipe 完全一样。 |
| 插件写入 UUID 后保存并重新加载 | — | 写在 `chat_metadata.echograph` 和 `swipe_info[k].extra` 里的 UUID 都保留了下来。 |
| 切换到已有的 swipe | `MESSAGE_SWIPED(i)` | `message.extra` 会换成目标 swipe 的那一份，UUID 跟着切换，正确。 |
| `/addswipe` 添加 swipe | **没有事件** | 只能靠核对发现。 |
| 编辑消息 | `MESSAGE_EDITED(i)`、`MESSAGE_UPDATED(i)` | UUID 不变，内容变了。要靠内容 hash 判断有没有被编辑。 |
| 隐藏和取消隐藏 | **没有事件** | 只是把 `is_system` 改成 `true` 或 `false`。 |
| `/sys` 旁白 | `MESSAGE_SENT` | `is_system` 是空值，`extra.type='narrator'`。可见“`is_system===true`”就等于用户隐藏了这条消息（其他系统消息类型还要 Codex 核实）。 |
| `/cut` 删除 | `MESSAGE_DELETED(新长度)` | 和读源码的结论一致。 |
| 创建检查点 | **没有事件** | 还停留在原聊天里。原消息的 `extra.bookmark_link` 记下了检查点的文件名。 |
| 创建分支 | `CHAT_CHANGED` | 自动切到新文件。`main_chat` 记的是父聊天的文件名。 |
| 分支或检查点的元数据 | — | **整份复制了父聊天的 `echograph.chat_uuid`**，消息 UUID 也原样复制。`integrity` 是新生成的。 |
| 重命名 | `CHAT_CHANGED`、`CHAT_RENAMED` | `chat_uuid` 和 `integrity` 都不变。 |
| 重命名父聊天之后 | — | 子聊天的 `main_chat` **没有更新**，仍然是旧的文件名。 |

**结论：检查点和分支不需要侵入式拦截。** 子聊天打开时，它的 `chat_uuid` 已经属于另一个聊天，而且 `integrity` 不一样，由此就能判断它是派生出来的：

- 父聊天：由复制过来的 `chat_uuid` 找到，不依赖 `main_chat`，所以不怕父聊天改名。
- 分叉点：从头比对父子两个聊天的消息 UUID 和内容 hash，最长的那段相同前缀的结尾就是分叉点。
- 父聊天之后即使又被编辑过，只要每一轮的历史增量都还保留，照样能还原出分叉那一刻的图谱。
- 子聊天会被分配一个新的 `chat_uuid`。

聊天身份由 `(chat_uuid, integrity)` 两个值一起确定。导入的副本两个值都和原聊天一样，需要按文件名区分。

另外两点：

- `/cut`、`/del`、`/branch-create`、`/checkpoint-create`、`/renamechat`、`/hide`、`/unhide` 这些斜杠命令都存在。第一轮报告说没找到 `/cut` 和 `/del`，那是错的。
- 第三方扩展 LittleWhiteBox 的 story-summary 模块也在跟踪 swipe、编辑和删除，可以参考它是怎么做的。用户的聊天元数据里也有其他扩展写入的字段，我们的字段必须放在 `echograph` 这个命名空间下面。

### 9.2.2 代码调查结果（Codex 第二轮，读源码）

- **开局**：
  - 酒馆创建开局时**没有**替换 `{{user}}` 和 `{{char}}` 这类宏，只在生成时才替换。所以要以当前 `mes` 的内容为准。
  - 聊天被标记为 tainted 之后，在第 0 条上往右滑到头，可能会让 LLM 生成新的开局，所以第 0 轮也可能出现 LLM 生成的 swipe。
  - 插件现在直接跳过 `first_message`；后端初始化时还把 `first_mes` 放进了基础图。这两处都和 R11 冲突，需要改。
- **世界书**：
  - 一共有 6 种来源：
    - 角色主绑定：`extensions.world`
    - 角色附加绑定：`charLore`
    - 卡内嵌世界书：`character_book`
    - 全局：`selected_world_info`
    - 聊天绑定：`chat_metadata.world_info`
    - Persona 绑定
  - 插件可以用 `getContext().loadWorldInfo(name)` 按书名逐本读取。不能用 `getSortedEntries()`，它会把所有来源合在一起，分不出哪条来自哪本书。
  - 插件现在读世界书的代码有 bug：`getWorldInfoPrompt()` 返回的是对象，插件却只接受字符串。结果是绑定的世界书基本都读不到。
- **基础图的 hash**：
  - 计入：角色卡里的文本字段，加上属于基础图的世界书条目（`uid/key/keysecondary/content/disable`）。所有内容规范化并按固定顺序排列后再计算。
  - 排除：开局、头像、标签。
- **隐藏消息**：
  - 隐藏只会把 `is_system` 改成 `true`，没有专门的标记。
  - 系统通知、`/comment` 和工具调用消息本来就是 `is_system=true`，可以用 `extra.type` 和 `extra.tool_invocations` 把它们排除。
  - 以后插件发现消息被隐藏时，要自己写一个持久标记。
- **上下文大小**：
  - `model_catalog` 能读到 `context_length` 等字段，但这个值目前没有存进配置。
  - 分段要按 **EchoGraph 自己配置的提取模型**来算，而不是酒馆用的模型，所以要在配置里加一个“模型上下文大小”字段。
- **本地模式**：
  - 消息格式是 `{role, content, timestamp}`，没有 ID、swipe 和分支。
  - 现在的“重新生成”会直接覆盖原回复；删除消息不会回滚图谱。
  - 本地模式的图谱更新在桌面程序里直接完成，不经过后台。
  - 并没有固定的 0 号对话：聊天列表为空时，会弹框问你是否创建示例；“新建对话”之后也会弹同一个询问框。这和 R16 不一致。
- **提取和增量**：
  - 逐轮更新时 LLM 能返回 add/update/delete 操作，但没有 `update_edge`。
  - 后台的延迟更新路径会**忽略删除操作**；本地路径会处理删除。两条路径的行为不一致。
  - 图谱用的是 `DiGraph`，同一对节点之间只能有一条同方向的边。
  - 更新 Agent 出错时会返回空结果，结果被当成“这一轮成功了，只是没有变化”。时间线引擎里必须把这种情况当作失败。
  - 增量要在“校验并真正写入图谱之后”记录下每处变化的 before 和 after，不能只存 LLM 返回的原始操作。

### 10.1 P1 设计要点

- **段（turn）**：
  - 先去掉不进图谱的消息（R21），剩下的消息按用户消息切分。开局单独成为第 0 段。
  - 每段包含一条或几条用户消息，加上紧跟其后的角色回复和旁白。
  - 末尾只有用户消息、还没有回复的那一段，暂不处理。
- **链式 key**：`key_0 = H(基础图 hash, 第 0 段内容)`，`key_k = H(key_{k-1}, 第 k 段内容 hash)`。每段的增量都按 key 存储，这样前面任何内容变了，后面的 key 会跟着全部改变。由此自然得到：
  - 编辑或隐藏第 N 段：从第 N 段开始，后面的 key 全部变化，需要重新提取（R14、R12）。
  - 切回一个已经生成过的 swipe：key 和以前一样，直接命中已存的增量，不调用 LLM（R13）。
  - 删除和回退：新时间线是旧时间线的前缀，直接用已有的 key，不调用 LLM。
  - 分支和检查点：和父聊天共同的那段前缀 key 完全相同，直接复用父聊天的增量。不需要单独计算分叉点，父聊天以后被修改也不影响（R3）。
- **增量**：在校验之后、写入图谱之后记录，每处变化都带 before 和 after；每隔若干段再存一份完整快照。
- **基础图**：按 hash 存储，旧版本保留。每个聊天固定使用它创建时的那个基础图版本（R8a）。
- **失败处理**：已经成功的段照常按 key 保存下来。只有所有待处理的段都成功后，聊天的 head 才会前进；在此之前，当前图谱保持原来的样子，并标记为“不一致”（5.4 节）。
- **图谱结构**：时间线引擎使用自己的图状态结构，支持多重边，每条边有稳定 ID（R23）。把现有的 `KnowledgeGraph` 和界面切换到这套结构上，放到 P2 和 P3 接线时再做。P1 不改动任何现有行为。

本地模式（P3）排在插件（P4）前面，是因为本地模式不需要打开酒馆，可以先拿它把核心逻辑测透。
